Reliable event delivery for document workflows

The problem

A document update had to save the change in PostgreSQL and notify other services through RabbitMQ. If the database commit succeeded and the process stopped before sending the message, the document would show its new state while downstream services would have no record of the change.

What I built

I implemented a transactional outbox in Python. The service wrote the document change and its outgoing event in the same PostgreSQL transaction. Once that transaction committed, a separate outbox processor could publish the event to RabbitMQ. If publication failed, the event remained available for another attempt.

Why the consumer mattered

Retries solved one problem and introduced another. Suppose RabbitMQ accepts a message, but the publisher stops before recording that it sent it. On recovery, the publisher can send the same event again.

I built idempotent consumers so that processing the same event twice had the same business effect as processing it once. For a document workflow, that means a duplicate delivery can arrive without repeating the corresponding update.

Result

A committed document change could survive a temporary broker outage with its event still waiting to be published. When delivery resumed, consumers could safely handle repeats. This let the document service complete its database transaction even when downstream processing had to wait.

Run the demo

I built a standalone demo to reproduce two failures: a broker outage and a consumer crash after commit but before acknowledgement. Run either experiment with Docker Compose or Kubernetes and check that the document history contains one entry.
